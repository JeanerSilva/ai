### Origem do OAuth 2.0

OAuth 2.0 é um protocolo de autorização que foi desenvolvido como uma evolução do OAuth 1.0, lançado em 2007. A versão 2.0 foi publicada em outubro de 2012 pelo Internet Engineering Task Force (IETF) como RFC 6749. O objetivo principal do OAuth 2.0 é permitir que aplicativos de terceiros obtenham acesso limitado a recursos de um usuário hospedados em um servidor, sem expor as credenciais do usuário.

### Conceitos do OAuth 2.0

1. **Resource Owner (Proprietário do Recurso)**: O usuário que autoriza um aplicativo a acessar seus recursos.
2. **Client (Cliente)**: O aplicativo que solicita acesso aos recursos do usuário.
3. **Resource Server (Servidor de Recursos)**: O servidor que hospeda os recursos protegidos.
4. **Authorization Server (Servidor de Autorização)**: O servidor que autentica o usuário e emite tokens de acesso.
5. **Access Token (Token de Acesso)**: Um token que concede ao cliente acesso aos recursos do usuário.
6. **Refresh Token (Token de Atualização)**: Um token que pode ser usado para obter um novo token de acesso quando o atual expirar.

### Tipos de OAuth 2.0

OAuth 2.0 define quatro tipos principais de concessão (grant types), cada um adequado para diferentes cenários de uso:

1. **Authorization Code Grant**
2. **Implicit Grant**
3. **Resource Owner Password Credentials Grant**
4. **Client Credentials Grant**

#### 1. Authorization Code Grant

- **Descrição**: Este é o tipo mais comum e seguro, utilizado principalmente por aplicativos web.
- **Fluxo**:
  1. O cliente redireciona o usuário para o servidor de autorização.
  2. O usuário autentica e autoriza o cliente.
  3. O servidor de autorização redireciona o usuário de volta ao cliente com um código de autorização.
  4. O cliente troca o código de autorização por um token de acesso no servidor de autorização.
- **Características**:
  - Requer um servidor de backend para armazenar o client secret.
  - Minimiza a exposição do token de acesso.

#### 2. Implicit Grant

- **Descrição**: Utilizado principalmente por aplicativos de uma única página (SPA) e aplicativos móveis.
- **Fluxo**:
  1. O cliente redireciona o usuário para o servidor de autorização.
  2. O usuário autentica e autoriza o cliente.
  3. O servidor de autorização redireciona o usuário de volta ao cliente com um token de acesso.
- **Características**:
  - Não requer um servidor de backend.
  - Menos seguro, pois o token de acesso é exposto diretamente no URL.

#### 3. Resource Owner Password Credentials Grant

- **Descrição**: Utilizado quando o cliente é confiável e o usuário confia no cliente com suas credenciais.
- **Fluxo**:
  1. O usuário fornece suas credenciais diretamente ao cliente.
  2. O cliente envia as credenciais ao servidor de autorização.
  3. O servidor de autorização emite um token de acesso.
- **Características**:
  - Requer alta confiança entre o usuário e o cliente.
  - Não recomendado para aplicativos de terceiros.

#### 4. Client Credentials Grant

- **Descrição**: Utilizado quando o cliente precisa acessar seus próprios recursos no servidor de recursos.
- **Fluxo**:
  1. O cliente autentica diretamente com o servidor de autorização usando suas próprias credenciais.
  2. O servidor de autorização emite um token de acesso.
- **Características**:
  - Não envolve um usuário final.
  - Utilizado para comunicação entre servidores.

### Classificações Adicionais

Além dos tipos principais de concessão, OAuth 2.0 também suporta extensões e variações, como:

- **Device Code Grant**: Utilizado para dispositivos com capacidade de entrada limitada, como TVs inteligentes.
- **JWT Bearer Token Grant**: Utilizado para troca de tokens JWT (JSON Web Tokens).
- **SAML 2.0 Bearer Assertion Grant**: Utilizado para troca de asserções SAML (Security Assertion Markup Language).

Cada um desses tipos e extensões tem suas próprias características e casos de uso específicos, permitindo uma flexibilidade considerável na implementação de soluções de autorização seguras e eficientes.
