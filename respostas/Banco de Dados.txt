BANCOS DE DADOS:: 01 SGBDs SQL e NOSQL.
Sistemas de Gerenciamento de Banco de Dados (SGBDs)
Origem
Os Sistemas de Gerenciamento de Banco de Dados (SGBDs) surgiram na década de 1960 para resolver problemas de armazenamento e recuperação de grandes volumes de dados. Com o avanço da tecnologia e a crescente necessidade de gerenciar dados de maneira eficiente, os SGBDs evoluíram para incluir diversas funcionalidades e suportar diferentes modelos de dados.
SGBDs SQL
Conceitos
SQL (Structured Query Language) é uma linguagem padrão para gerenciamento de bancos de dados relacionais. Os SGBDs SQL utilizam um modelo de dados relacional, onde os dados são organizados em tabelas com linhas e colunas. A integridade dos dados é mantida através de restrições e chaves primárias/estrangeiras.
Tipos e Classificações
1. SGBDs Relacionais (RDBMS)
o Exemplos: MySQL, PostgreSQL, Oracle, Microsoft SQL Server
o Características: 
• Utilizam tabelas para armazenar dados.
• Suportam ACID (Atomicidade, Consistência, Isolamento, Durabilidade).
• Utilizam SQL para manipulação e consulta de dados.
• Suportam transações e garantem a integridade dos dados.
2. SGBDs Relacionais Distribuídos
o Exemplos: Google Spanner, CockroachDB
o Características: 
• Distribuem dados em múltiplos servidores.
• Oferecem alta disponibilidade e tolerância a falhas.
• Mantêm a consistência dos dados através de mecanismos de sincronização.
SGBDs NoSQL
Conceitos
NoSQL (Not Only SQL) refere-se a uma classe de sistemas de gerenciamento de banco de dados que não utilizam o modelo relacional tradicional. Esses sistemas são projetados para lidar com grandes volumes de dados, alta velocidade de leitura/escrita e escalabilidade horizontal.
Tipos e Classificações
1. Bancos de Dados de Documentos
o Exemplos: MongoDB, CouchDB
o Características: 
• Armazenam dados em documentos (geralmente JSON ou BSON).
• Flexibilidade na estrutura dos dados.
• Suportam consultas complexas e indexação.
2. Bancos de Dados de Colunas
o Exemplos: Apache Cassandra, HBase
o Características: 
• Armazenam dados em colunas em vez de linhas.
• Otimizados para leitura e escrita rápidas.
• Escalabilidade horizontal e alta disponibilidade.
3. Bancos de Dados de Chave-Valor
o Exemplos: Redis, DynamoDB
o Características: 
• Armazenam dados como pares chave-valor.
• Simplicidade e alta performance.
• Ideal para caches e armazenamento de sessões.
4. Bancos de Dados de Grafos
o Exemplos: Neo4j, Amazon Neptune
o Características: 
• Armazenam dados em nós e arestas (grafo).
• Otimizados para consultas de relacionamento.
• Utilizados em redes sociais, recomendações e análise de fraudes.
5. Bancos de Dados de Tempo Real
o Exemplos: InfluxDB, TimescaleDB
o Características: 
• Otimizados para armazenar e consultar séries temporais.
• Suportam agregações e análises em tempo real.
• Utilizados em monitoramento de sistemas, IoT e análise de dados temporais.
Conclusão
Os SGBDs SQL e NoSQL oferecem diferentes abordagens para o gerenciamento de dados, cada um com suas próprias vantagens e desvantagens. A escolha entre SQL e NoSQL depende das necessidades específicas do projeto, como a estrutura dos dados, a necessidade de escalabilidade, a complexidade das consultas e os requisitos de consistência e integridade dos dados.
BANCOS DE DADOS:: 02 Modelagens de dados:
Claro! Vamos abordar duas modelagens de dados amplamente utilizadas: o Modelo Entidade-Relacionamento (ER) e o Modelo Relacional.
1. Modelo Entidade-Relacionamento (ER)
Origem:
O Modelo Entidade-Relacionamento foi proposto por Peter Chen em 1976. Ele foi desenvolvido para facilitar a concepção de bancos de dados, permitindo uma representação mais intuitiva e visual das estruturas de dados.
Conceitos:
• Entidade: Representa um objeto ou conceito do mundo real que pode ser identificado de forma única. Exemplo: Cliente, Produto.
• Atributo: Características ou propriedades de uma entidade. Exemplo: Nome, Idade, Endereço.
• Relacionamento: Descreve como duas ou mais entidades estão associadas. Exemplo: Um Cliente compra um Produto.
• Cardinalidade: Define o número de ocorrências de uma entidade que pode estar associada a ocorrências de outra entidade. Exemplo: Um para Um (1:1), Um para Muitos (1:N), Muitos para Muitos (M:N).
Tipos e Classificações:
• Entidades Fortes: Entidades que possuem uma existência independente no banco de dados.
• Entidades Fracas: Entidades que dependem de outra entidade para existir.
• Relacionamentos Binários: Envolvem duas entidades.
• Relacionamentos Ternários: Envolvem três entidades.
• Atributos Simples: Não podem ser divididos em subpartes. Exemplo: Número de Identificação.
• Atributos Compostos: Podem ser divididos em subpartes. Exemplo: Endereço (Rua, Cidade, Estado).
• Atributos Monovalorados: Contêm um único valor. Exemplo: Data de Nascimento.
• Atributos Multivalorados: Podem conter múltiplos valores. Exemplo: Telefones de Contato.
2. Modelo Relacional
Origem:
O Modelo Relacional foi introduzido por Edgar F. Codd em 1970. Ele revolucionou a forma como os dados são armazenados e manipulados, utilizando tabelas (ou relações) para representar dados e suas inter-relações.
Conceitos:
• Tabela (Relação): Conjunto de linhas e colunas onde os dados são armazenados. Cada tabela representa uma entidade ou um relacionamento.
• Linha (Tupla): Representa um registro individual na tabela.
• Coluna (Atributo): Representa uma característica ou propriedade da entidade.
• Chave Primária: Um ou mais atributos que identificam de forma única uma tupla em uma tabela.
• Chave Estrangeira: Um ou mais atributos que criam um vínculo entre duas tabelas, referenciando a chave primária de outra tabela.
• Integridade Referencial: Garante que as relações entre tabelas permaneçam consistentes.
Tipos e Classificações:
• Tabelas Base: Tabelas que armazenam dados reais.
• Visões (Views): Tabelas virtuais criadas a partir de consultas em uma ou mais tabelas base.
• Chaves Primárias: Atributos ou combinações de atributos que identificam unicamente uma tupla.
• Chaves Estrangeiras: Atributos que referenciam chaves primárias de outras tabelas para manter a integridade referencial.
• Índices: Estruturas que melhoram a velocidade de recuperação de dados.
• Restrições de Integridade: 
o Integridade de Entidade: Nenhuma parte da chave primária pode ser nula.
o Integridade Referencial: Cada valor de chave estrangeira deve corresponder a um valor de chave primária existente.
o Integridade de Domínio: Os valores dos atributos devem ser válidos dentro do domínio especificado.
Características dos Tipos:
Modelo Entidade-Relacionamento:
• Entidades Fortes: Independentes, possuem chave primária própria.
• Entidades Fracas: Dependem de entidades fortes, possuem chave parcial.
• Relacionamentos Binários: Simples, entre duas entidades.
• Relacionamentos Ternários: Complexos, entre três entidades.
• Atributos Simples: Indivisíveis.
• Atributos Compostos: Divisíveis em subpartes.
• Atributos Monovalorados: Um único valor por entidade.
• Atributos Multivalorados: Múltiplos valores por entidade.
Modelo Relacional:
• Tabelas Base: Armazenam dados reais.
• Visões: Tabelas virtuais, derivadas de consultas.

Modelagem de Dados Relacional
Origem
A modelagem de dados relacional foi introduzida por Edgar F. Codd em 1970 enquanto trabalhava na IBM. Codd propôs o modelo relacional como uma maneira de estruturar e consultar dados em bancos de dados, utilizando a teoria dos conjuntos e a lógica de predicados. Este modelo revolucionou a forma como os dados eram armazenados e manipulados, levando ao desenvolvimento de sistemas de gerenciamento de banco de dados relacionais (RDBMS) como Oracle, MySQL, SQL Server, entre outros.
Conceitos
1. Tabela (Relação): Estrutura básica que armazena dados em linhas e colunas.
2. Linha (Tupla): Representa um único registro na tabela.
3. Coluna (Atributo): Representa um campo de dados dentro de uma tabela.
4. Chave Primária: Um ou mais atributos que identificam unicamente uma tupla em uma tabela.
5. Chave Estrangeira: Um ou mais atributos que criam um vínculo entre duas tabelas.
6. Índice: Estrutura que melhora a velocidade das operações de consulta.
7. Normalização: Processo de organizar os dados para reduzir a redundância e melhorar a integridade dos dados.
8. Consulta (Query): Comando utilizado para recuperar dados de um banco de dados.
Tipos e Classificações
1. Modelos de Dados
• Modelo Conceitual: Representa a estrutura de dados de forma abstrata, sem considerar detalhes técnicos. Utiliza diagramas de entidade-relacionamento (ER) para descrever entidades, atributos e relacionamentos.
• Modelo Lógico: Traduz o modelo conceitual em uma estrutura que pode ser implementada em um RDBMS. Define tabelas, colunas, tipos de dados, chaves primárias e estrangeiras.
• Modelo Físico: Detalha a implementação do modelo lógico no sistema de banco de dados específico, incluindo índices, partições e outros aspectos de desempenho.
2. Normalização
• Primeira Forma Normal (1NF): Elimina grupos repetitivos, garantindo que cada coluna contenha apenas valores atômicos.
• Segunda Forma Normal (2NF): Garante que todos os atributos não-chave sejam totalmente dependentes da chave primária.
• Terceira Forma Normal (3NF): Remove dependências transitivas, garantindo que atributos não-chave não dependam de outros atributos não-chave.
• Forma Normal de Boyce-Codd (BCNF): Uma versão mais rigorosa da 3NF, onde cada determinante é uma chave candidata.
• Quarta Forma Normal (4NF): Elimina dependências multivaloradas.
• Quinta Forma Normal (5NF): Trata de decomposições que não podem ser mais divididas sem perder informações.
3. Tipos de Relacionamentos
• Um-para-Um (1:1): Cada registro em uma tabela está associado a um único registro em outra tabela.
• Um-para-Muitos (1:N): Um registro em uma tabela pode estar associado a múltiplos registros em outra tabela.
• Muitos-para-Muitos (N:M): Múltiplos registros em uma tabela podem estar associados a múltiplos registros em outra tabela, geralmente implementado através de uma tabela intermediária.
4. Tipos de Chaves
• Chave Primária (Primary Key): Identifica unicamente cada registro em uma tabela.
• Chave Estrangeira (Foreign Key): Mantém a integridade referencial entre duas tabelas.
• Chave Candidata (Candidate Key): Um conjunto de atributos que podem ser usados como chave primária.
• Chave Alternativa (Alternate Key): Qualquer chave candidata que não seja a chave primária.
• Chave Composta (Composite Key): Uma chave primária que consiste em mais de um atributo.
5. Índices
• Índice Clusterizado (Clustered Index): Reorganiza a tabela física para corresponder à ordem do índice.
• Índice Não-Clusterizado (Non-Clustered Index): Mantém uma estrutura separada que aponta para os dados reais.
• Índice Único (Unique Index): Garante que todos os valores no índice sejam distintos.
• Índice de Texto Completo (Full-Text Index): Otimiza a busca de texto em colunas de texto.

BANCOS DE DADOS:: 02.2 Modelagens de dados multidimensional,
Modelagens de Dados Multidimensional
Origem
A modelagem de dados multidimensional surgiu no contexto de sistemas de suporte à decisão e data warehousing. A necessidade de analisar grandes volumes de dados de maneira eficiente levou ao desenvolvimento de técnicas que permitissem a visualização e manipulação de dados em múltiplas dimensões. Ralph Kimball e Bill Inmon são dois dos principais pioneiros nesse campo, com Kimball sendo particularmente conhecido por popularizar o modelo dimensional.
Conceitos
A modelagem de dados multidimensional é uma abordagem que organiza dados em um formato que facilita a análise e a consulta rápida. Os principais conceitos incluem:
• Dimensões: Representam os diferentes aspectos ou perspectivas a partir dos quais os dados podem ser analisados, como tempo, localização, produto, etc.
• Fatos: São os dados numéricos ou métricas que os usuários desejam analisar, como vendas, lucros, etc.
• Cubos: Estruturas de dados que permitem a visualização de dados em múltiplas dimensões.
• Hierarquias: Estruturas dentro das dimensões que permitem a agregação de dados em diferentes níveis de detalhe, como ano, trimestre, mês, dia.
Tipos e Classificações
1. Modelos Estrela (Star Schema)
o Características: 
• Consiste em uma tabela de fatos central conectada a várias tabelas de dimensões.
• Simplicidade e facilidade de entendimento.
• Desempenho eficiente para consultas simples.
o Exemplo: 
• Uma tabela de fatos de vendas conectada a tabelas de dimensões de tempo, produto e localização.
2. Modelos Floco de Neve (Snowflake Schema)
o Características: 
• Extensão do modelo estrela onde as tabelas de dimensões são normalizadas.
• Redução de redundância de dados.
• Consultas podem ser mais complexas e menos eficientes devido a múltiplas junções.
o Exemplo: 
• Uma tabela de fatos de vendas conectada a uma tabela de dimensão de produto, que por sua vez está conectada a tabelas de subdimensões como categoria de produto e fornecedor.
3. Modelos Constelação de Fatos (Fact Constellation Schema)
o Características: 
• Consiste em múltiplas tabelas de fatos que compartilham dimensões comuns.
• Suporta análises complexas e relacionamentos entre diferentes processos de negócios.
• Pode ser mais difícil de gerenciar e entender.
o Exemplo: 
• Tabelas de fatos de vendas e inventário compartilhando dimensões de tempo, produto e localização.
4. Modelos Galáxia (Galaxy Schema)
o Características: 
• Similar ao modelo constelação de fatos, mas em uma escala maior.
• Utilizado em grandes data warehouses que suportam múltiplos processos de negócios.
• Alta complexidade e necessidade de gerenciamento robusto.
o Exemplo: 
• Um data warehouse corporativo que inclui tabelas de fatos para vendas, inventário, marketing e finanças, todas compartilhando dimensões comuns.
5. Modelos de Cubo OLAP (Online Analytical Processing)
o Características: 
• Estruturas de dados tridimensionais ou multidimensionais que permitem a análise rápida e interativa.
• Suporte a operações como drill-down, roll-up, slice e dice.
• Pode ser implementado em MOLAP (Multidimensional OLAP), ROLAP (Relational OLAP) ou HOLAP (Hybrid OLAP).
o Exemplo: 
• Um cubo OLAP que permite a análise de vendas por produto, região e tempo, com a capacidade de detalhar até o nível de dia ou agregar até o nível de ano.
Conclusão
A modelagem de dados multidimensional é uma técnica poderosa para a análise de dados em sistemas de suporte à decisão. Com diferentes tipos e classificações, como os modelos estrela, floco de neve, constelação de fatos, galáxia e cubos OLAP, essa abordagem oferece flexibilidade e eficiência para atender às diversas necessidades analíticas das organizações.
BANCOS DE DADOS:: 02.3 Modelagens de dados nosql.
Origem e Conceitos de Modelagens de Dados NoSQL
A modelagem de dados NoSQL surgiu como uma resposta às limitações dos bancos de dados relacionais tradicionais (SQL) em lidar com grandes volumes de dados, alta velocidade de leitura e escrita, e a necessidade de escalabilidade horizontal. Com o advento da web 2.0, redes sociais, big data e a Internet das Coisas (IoT), a necessidade de sistemas de banco de dados que pudessem lidar com dados não estruturados e semi-estruturados cresceu exponencialmente. NoSQL, que significa “Not Only SQL”, refere-se a uma classe de sistemas de gerenciamento de banco de dados que não seguem o modelo relacional tradicional.
Conceitos Principais:
1. Escalabilidade Horizontal: Capacidade de adicionar mais servidores para distribuir a carga de trabalho.
2. Flexibilidade de Esquema: Permite a inserção de dados sem a necessidade de definir um esquema fixo.
3. Alta Disponibilidade: Sistemas projetados para minimizar o tempo de inatividade.
4. Desempenho: Otimizado para operações de leitura e escrita rápidas.
5. Consistência Eventual: Em vez de garantir a consistência imediata dos dados, alguns sistemas NoSQL garantem que, eventualmente, todos os dados serão consistentes.
Tipos e Classificações de Modelagens de Dados NoSQL
Os bancos de dados NoSQL podem ser classificados em quatro tipos principais, cada um com suas características e casos de uso específicos:
1. Bancos de Dados de Chave-Valor (Key-Value Stores):
o Características: Armazenam dados como pares de chave-valor. A chave é única e usada para recuperar o valor associado.
o Exemplos: Redis, DynamoDB, Riak.
o Casos de Uso: Sessões de usuário, carrinhos de compras, cache.
2. Bancos de Dados de Colunas (Column-Family Stores):
o Características: Armazenam dados em tabelas, linhas e colunas, mas diferem dos bancos de dados relacionais ao permitir que cada linha tenha um número diferente de colunas.
o Exemplos: Apache Cassandra, HBase.
o Casos de Uso: Análise de grandes volumes de dados, logs de eventos, sistemas de recomendação.
3. Bancos de Dados de Documentos (Document Stores):
o Características: Armazenam dados em documentos, geralmente no formato JSON, BSON ou XML. Cada documento é uma unidade autônoma que pode conter dados complexos e aninhados.
o Exemplos: MongoDB, CouchDB.
o Casos de Uso: Gerenciamento de conteúdo, e-commerce, aplicativos móveis.
4. Bancos de Dados de Grafos (Graph Databases):
o Características: Armazenam dados em nós, arestas e propriedades, permitindo a representação de relações complexas entre dados.
o Exemplos: Neo4j, Amazon Neptune.
o Casos de Uso: Redes sociais, sistemas de recomendação, detecção de fraudes.
Detalhamento dos Tipos e Suas Características:
1. Bancos de Dados de Chave-Valor:
o Redis: Armazenamento em memória, extremamente rápido, suporta estruturas de dados como listas, conjuntos e hashes.
o DynamoDB: Serviço gerenciado pela AWS, oferece escalabilidade automática e replicação de dados.
o Riak: Distribuído, altamente disponível, baseado no modelo de consistência eventual.
2. Bancos de Dados de Colunas:
o Apache Cassandra: Distribuído, escalável, projetado para alta disponibilidade sem ponto único de falha.
o HBase: Baseado no HDFS (Hadoop Distributed File System), projetado para grandes tabelas dispersas.
3. Bancos de Dados de Documentos:
o MongoDB: Flexível, permite consultas ad hoc, indexação e agregação de dados.
o CouchDB: Utiliza JSON para armazenar dados, JavaScript para consultas e MapReduce para indexação.
4. Bancos de Dados de Grafos:
o Neo4j: Utiliza o modelo de grafo de propriedade, permite consultas complexas e rápidas sobre relações.
o Amazon Neptune: Serviço gerenciado, suporta os modelos de grafo Property Graph e RDF (Resource Description Framework).
Cada tipo de banco de dados NoSQL é projetado para atender a diferentes necessidades e casos de uso, oferecendo flexibilidade e desempenho onde os bancos de dados relacionais podem não ser a melhor escolha.
BANCOS DE DADOS:: 03 SQL Procedural Language
Resumo sobre SQL Procedural Language
Origem
SQL Procedural Language (PL/SQL) é uma extensão da linguagem SQL desenvolvida pela Oracle Corporation no final dos anos 1980. A ideia era adicionar capacidades procedurais à SQL, permitindo a criação de blocos de código que poderiam ser executados como unidades, facilitando a programação de lógica complexa diretamente no banco de dados.
Conceitos
SQL Procedural Language combina a simplicidade da SQL com a robustez das linguagens de programação procedurais. Os principais conceitos incluem:
1. Blocos de Código: Estruturas que agrupam declarações, comandos e exceções.
2. Variáveis e Tipos de Dados: Permitem armazenar e manipular dados temporários.
3. Controle de Fluxo: Estruturas como loops, condicionais e instruções de controle.
4. Procedures e Functions: Subprogramas que encapsulam lógica reutilizável.
5. Triggers: Blocos de código que são executados automaticamente em resposta a eventos no banco de dados.
6. Pacotes: Coleções de procedures, functions, variáveis e outros elementos que são agrupados logicamente.
Tipos e Classificações
1. Blocos Anônimos
o Características: Não têm nome e não são armazenados no banco de dados. São usados para tarefas ad-hoc.
o Exemplo:
o DECLARE
o   v_variable NUMBER;
o BEGIN
o   v_variable := 10;
o   DBMS_OUTPUT.PUT_LINE('Value: ' || v_variable);
o END;
2. Procedures
o Características: Subprogramas nomeados que podem aceitar parâmetros e não retornam valores diretamente.
o Exemplo:
o CREATE OR REPLACE PROCEDURE update_salary(emp_id NUMBER, new_salary NUMBER) IS
o BEGIN
o   UPDATE employees SET salary = new_salary WHERE employee_id = emp_id;
o END;
3. Functions
o Características: Subprogramas nomeados que podem aceitar parâmetros e retornam um valor.
o Exemplo:
o CREATE OR REPLACE FUNCTION get_employee_name(emp_id NUMBER) RETURN VARCHAR2 IS
o   v_name VARCHAR2(100);
o BEGIN
o   SELECT name INTO v_name FROM employees WHERE employee_id = emp_id;
o   RETURN v_name;
o END;
4. Triggers
o Características: Blocos de código que são executados automaticamente em resposta a eventos como INSERT, UPDATE ou DELETE.
o Tipos de Triggers: 
• Row-level Triggers: Executados para cada linha afetada.
• Statement-level Triggers: Executados uma vez por operação.
o Exemplo:
o CREATE OR REPLACE TRIGGER trg_before_insert
o BEFORE INSERT ON employees
o FOR EACH ROW
o BEGIN
o   :NEW.created_at := SYSDATE;
o END;

o Componentes: 
• Specification: Declarações públicas.
• Body: Implementações privadas.

BANCOS DE DADOS:: 03.1 SQL Structured Query Language.
SQL (Structured Query Language)
Origem:
SQL, ou Structured Query Language, é uma linguagem de programação padrão utilizada para gerenciar e manipular bancos de dados relacionais. Foi desenvolvida inicialmente na década de 1970 por Donald D. Chamberlin e Raymond F. Boyce nos laboratórios da IBM, como parte do projeto System R. A primeira versão comercial de SQL foi lançada pela Oracle em 1979. Desde então, SQL tornou-se o padrão de fato para interação com sistemas de gerenciamento de banco de dados (SGBDs) relacionais.
Conceitos:
SQL é usada para realizar várias operações em bancos de dados, incluindo a criação, leitura, atualização e exclusão de dados. Os principais conceitos de SQL incluem:
1. DDL (Data Definition Language): Utilizada para definir e gerenciar estruturas de banco de dados, como tabelas e índices.
2. DML (Data Manipulation Language): Utilizada para manipular dados dentro das estruturas de banco de dados.
3. DCL (Data Control Language): Utilizada para controlar o acesso aos dados no banco de dados.
4. TCL (Transaction Control Language): Utilizada para gerenciar transações no banco de dados.
Tipos e Classificações:
1. DDL (Data Definition Language):
o CREATE: Cria novas tabelas, índices, vistas, etc. 
• Exemplo: CREATE TABLE Employees (ID INT, Name VARCHAR(100));
o ALTER: Modifica a estrutura de uma tabela existente. 
• Exemplo: ALTER TABLE Employees ADD COLUMN Age INT;
o DROP: Remove tabelas, índices, vistas, etc. 
• Exemplo: DROP TABLE Employees;
o TRUNCATE: Remove todos os registros de uma tabela, mas mantém a estrutura. 
• Exemplo: TRUNCATE TABLE Employees;
2. DML (Data Manipulation Language):
o SELECT: Recupera dados de uma ou mais tabelas. 
• Exemplo: SELECT * FROM Employees;
o INSERT: Insere novos registros em uma tabela. 
• Exemplo: INSERT INTO Employees (ID, Name) VALUES (1, 'John Doe');
o UPDATE: Atualiza dados existentes em uma tabela. 
• Exemplo: UPDATE Employees SET Name = 'Jane Doe' WHERE ID = 1;
o DELETE: Remove registros de uma tabela. 
• Exemplo: DELETE FROM Employees WHERE ID = 1;
3. DCL (Data Control Language):
o GRANT: Concede permissões a usuários. 
• Exemplo: GRANT SELECT ON Employees TO User1;
o REVOKE: Revoga permissões de usuários. 
• Exemplo: REVOKE SELECT ON Employees FROM User1;
4. TCL (Transaction Control Language):
o COMMIT: Confirma uma transação, tornando todas as alterações permanentes. 
• Exemplo: COMMIT;
o ROLLBACK: Desfaz uma transação, revertendo todas as alterações feitas. 
• Exemplo: ROLLBACK;
o SAVEPOINT: Define um ponto dentro de uma transação para que seja possível fazer um rollback parcial. 
• Exemplo: SAVEPOINT Savepoint1;
o SET TRANSACTION: Define características de uma transação, como o nível de isolamento. 
• Exemplo: SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
Características dos Tipos:
• DDL: Foca na estrutura do banco de dados. As operações DDL são geralmente auto-commit, o que significa que uma vez executadas, não podem ser revertidas.
• DML: Foca na manipulação dos dados dentro das estruturas definidas pelo DDL. As operações DML podem ser revertidas se não forem confirmadas com um COMMIT.
• DCL: Foca no controle de acesso aos dados. Permite definir quem pode fazer o quê dentro do banco de dados.
• TCL: Foca na gestão de transações, garantindo a integridade e consistência dos dados durante operações complexas.
SQL é uma linguagem poderosa e essencial para a gestão de bancos de dados relacionais, oferecendo uma ampla gama de comandos para atender às necessidades de definição, manipulação, controle e transação de dados.
BANCOS DE DADOS:: 04 Arquitetura de Inteligência de Negócio.
Arquitetura de Inteligência de Negócio (BI)
Origem
A Inteligência de Negócio (BI) surgiu na década de 1960 como um sistema de compartilhamento de informações entre organizações. Na década de 1980, os sistemas de BI começaram a se desenvolver mais formalmente com a introdução de modelos de dados e sistemas de suporte à decisão. A partir dos anos 2000, com o avanço da tecnologia da informação e a explosão de dados, a BI evoluiu para incluir ferramentas mais sofisticadas de análise de dados, visualização e relatórios.
Conceitos
A Inteligência de Negócio refere-se ao uso de tecnologias, processos e aplicações para coletar, integrar, analisar e apresentar informações de negócios. O objetivo é apoiar a tomada de decisões informadas e estratégicas. Os principais conceitos incluem:
1. Data Warehousing: Armazenamento centralizado de dados de várias fontes.
2. ETL (Extract, Transform, Load): Processo de extração, transformação e carregamento de dados.
3. Data Mining: Análise de grandes conjuntos de dados para descobrir padrões e insights.
4. OLAP (Online Analytical Processing): Ferramentas que permitem a análise multidimensional de dados.
5. Dashboards e Relatórios: Ferramentas de visualização que apresentam dados de forma compreensível.
Tipos e Classificações
1. Arquitetura de Dados
o Data Warehousing: Armazena dados históricos de várias fontes para análise.
o Data Lakes: Armazena grandes volumes de dados brutos em seu formato nativo.
o Data Marts: Subconjuntos de data warehouses focados em áreas específicas de negócios.
2. Arquitetura de Processamento de Dados
o ETL (Extract, Transform, Load): Processo de mover dados de fontes diversas para um data warehouse.
o ELT (Extract, Load, Transform): Similar ao ETL, mas a transformação ocorre após o carregamento dos dados.
o Streaming Data Processing: Processamento de dados em tempo real à medida que são gerados.
3. Arquitetura de Análise de Dados
o OLAP (Online Analytical Processing): Permite a análise multidimensional de dados.
o Data Mining: Técnicas para descobrir padrões ocultos em grandes volumes de dados.
o Predictive Analytics: Uso de modelos estatísticos e algoritmos para prever tendências futuras.
4. Arquitetura de Apresentação de Dados
o Dashboards: Interfaces visuais que mostram métricas e KPIs em tempo real.
o Relatórios: Documentos que apresentam dados analisados de forma estruturada.
o Scorecards: Ferramentas que medem o desempenho em relação a objetivos estratégicos.
Detalhamento dos Tipos e suas Características
1. Arquitetura de Dados
o Data Warehousing: Centraliza dados históricos de várias fontes, facilitando a análise e relatórios. É otimizado para consultas complexas e análise de dados.
o Data Lakes: Armazena dados em seu formato bruto, permitindo maior flexibilidade na análise. Ideal para dados não estruturados e semi-estruturados.
o Data Marts: Focados em áreas específicas de negócios, como vendas ou finanças, permitindo análises mais rápidas e específicas.
2. Arquitetura de Processamento de Dados
o ETL (Extract, Transform, Load): Extrai dados de várias fontes, transforma-os para atender às necessidades de análise e carrega-os em um data warehouse.
o ELT (Extract, Load, Transform): Similar ao ETL, mas a transformação ocorre após o carregamento dos dados no data warehouse, aproveitando o poder de processamento do próprio data warehouse.
o Streaming Data Processing: Processa dados em tempo real, permitindo análises e ações imediatas. Utilizado em aplicações como monitoramento de redes sociais e detecção de fraudes.
3. Arquitetura de Análise de Dados
o OLAP (Online Analytical Processing): Permite a análise multidimensional de dados, facilitando a visualização de dados em diferentes perspectivas (por exemplo, por tempo, localização, produto).
o Data Mining: Utiliza algoritmos para descobrir padrões ocultos em grandes volumes de dados, como associações, sequências e clusters.
o Predictive Analytics: Utiliza modelos estatísticos e algoritmos de machine learning para prever tendências futuras e comportamentos, ajudando na tomada de decisões proativas.
4. Arquitetura de Apresentação de Dados
o Dashboards: Fornecem uma visão geral em tempo real das métricas e KPIs mais importantes, permitindo uma rápida tomada de decisão
BANCOS DE DADOS:: 04.1 DataWarehouse.
Origem do Data Warehouse
O conceito de Data Warehouse (DW) surgiu na década de 1980, com o objetivo de resolver problemas relacionados à integração e análise de grandes volumes de dados provenientes de diferentes fontes. Bill Inmon é frequentemente citado como o “pai do Data Warehouse”, tendo popularizado o termo e estabelecido muitos dos princípios fundamentais que ainda são seguidos hoje.
Conceitos de Data Warehouse
Um Data Warehouse é um sistema de armazenamento de dados projetado para facilitar a análise e o relatório de dados. Ele integra dados de múltiplas fontes heterogêneas, transformando-os em um formato consistente e acessível para análise. Os principais conceitos incluem:
1. Integração: Dados de diferentes fontes são combinados em um formato unificado.
2. Histórico: Armazena dados históricos para análise de tendências ao longo do tempo.
3. Não-volatilidade: Dados no DW não são alterados ou removidos, apenas adicionados.
4. Orientação por assunto: Dados são organizados por temas ou áreas de interesse, como vendas, finanças, etc.
Tipos e Classificações de Data Warehouse
Os Data Warehouses podem ser classificados de várias maneiras, dependendo de sua arquitetura, escopo e uso. Abaixo estão os principais tipos e suas características:
1. Enterprise Data Warehouse (EDW)
• Descrição: Um EDW é um repositório centralizado que consolida dados de toda a organização.
• Características: 
o Escalabilidade: Capaz de lidar com grandes volumes de dados.
o Integração: Integra dados de todas as áreas da empresa.
o Consistência: Garante a consistência dos dados em toda a organização.
o Flexibilidade: Suporta uma ampla gama de consultas e análises.
2. Data Mart
• Descrição: Um Data Mart é uma versão menor e mais focada de um Data Warehouse, geralmente voltada para um departamento ou área específica da organização.
• Características: 
o Escopo limitado: Focado em um único departamento ou área de negócio.
o Implementação rápida: Pode ser implementado mais rapidamente do que um EDW.
o Menor custo: Geralmente menos caro de implementar e manter.
o Facilidade de uso: Mais fácil de usar e gerenciar devido ao seu escopo limitado.
3. Operational Data Store (ODS)
• Descrição: Um ODS é um tipo de Data Warehouse que é atualizado em tempo real e é usado para operações diárias.
• Características: 
o Atualização em tempo real: Dados são atualizados continuamente.
o Suporte a operações: Usado para operações diárias e não apenas para análise histórica.
o Integração de dados operacionais: Combina dados de sistemas operacionais diferentes.
o Menor histórico: Geralmente mantém dados por um período mais curto em comparação com um EDW.
4. Virtual Data Warehouse
• Descrição: Um Virtual Data Warehouse não armazena dados fisicamente, mas fornece uma visão unificada dos dados armazenados em diferentes sistemas.
• Características: 
o Sem armazenamento físico: Não armazena dados em um único local.
o Acesso em tempo real: Fornece acesso em tempo real aos dados.
o Flexibilidade: Pode ser rapidamente ajustado para incluir novas fontes de dados.
o Menor custo inicial: Menor custo inicial de implementação, pois não requer infraestrutura de armazenamento.
Conclusão
Os Data Warehouses são fundamentais para a análise de dados e a tomada de decisões informadas em organizações modernas. Eles podem variar em escopo e complexidade, desde grandes Enterprise Data Warehouses que abrangem toda a organização até Data Marts focados em departamentos específicos. A escolha do tipo de Data Warehouse depende das necessidades específicas da organização, incluindo o volume de dados, a necessidade de integração e a velocidade de acesso aos dados.
BANCOS DE DADOS:: 04.2 DataMart.
DataMart: Origem, Conceitos, Tipos e Classificações
Origem
O conceito de DataMart surgiu como uma solução para a necessidade de análise de dados em áreas específicas de uma organização. Enquanto os Data Warehouses (DW) são grandes repositórios de dados que abrangem toda a empresa, os DataMarts são subconjuntos desses dados, focados em departamentos ou áreas de negócio específicas, como vendas, marketing ou finanças. A ideia é fornecer uma visão mais focada e acessível dos dados, facilitando a tomada de decisões em níveis mais operacionais.
Conceitos
• DataMart: Um DataMart é um repositório de dados orientado a um departamento ou área específica de uma organização. Ele é projetado para atender às necessidades de análise e relatórios de um grupo específico de usuários.
• Data Warehouse: Um repositório centralizado que armazena dados de toda a organização, integrando informações de várias fontes.
• ETL (Extract, Transform, Load): Processo de extração, transformação e carregamento de dados, essencial para a criação e manutenção de DataMarts.
Tipos e Classificações de DataMarts
Os DataMarts podem ser classificados de várias maneiras, dependendo de sua arquitetura, funcionalidade e implementação. Abaixo estão os principais tipos e suas características:
1. DataMarts Dependentes
o Descrição: São criados a partir de um Data Warehouse centralizado. Os dados são extraídos do Data Warehouse, transformados conforme necessário e carregados no DataMart.
o Características: 
• Alta consistência de dados, pois todos os DataMarts dependem de uma única fonte de verdade.
• Facilita a governança de dados e a conformidade com políticas de segurança.
• Pode ser mais complexo e caro de implementar devido à necessidade de um Data Warehouse centralizado.
2. DataMarts Independentes
o Descrição: São criados diretamente a partir de fontes de dados operacionais, sem a necessidade de um Data Warehouse centralizado.
o Características: 
• Mais rápidos e baratos de implementar, pois não requerem a criação de um Data Warehouse.
• Podem levar a inconsistências de dados, já que cada DataMart pode ter sua própria versão dos dados.
• Menos controle centralizado, o que pode dificultar a governança de dados.
3. DataMarts Híbridos
o Descrição: Combinam características de DataMarts dependentes e independentes. Podem extrair dados tanto de um Data Warehouse centralizado quanto de fontes operacionais.
o Características: 
• Flexibilidade para atender a diferentes necessidades de dados.
• Pode equilibrar a necessidade de consistência de dados com a necessidade de rapidez e custo.
• Complexidade intermediária em termos de implementação e manutenção.
4. DataMarts Baseados em Nuvem
o Descrição: São implementados em plataformas de nuvem, como AWS, Google Cloud ou Azure.
o Características: 
• Escalabilidade e flexibilidade para lidar com grandes volumes de dados.
• Redução de custos de infraestrutura, pois não requerem hardware local.
• Facilidade de integração com outras ferramentas e serviços baseados em nuvem.
5. DataMarts de Aplicação
o Descrição: São projetados para suportar aplicações específicas, como CRM (Customer Relationship Management) ou ERP (Enterprise Resource Planning).
o Características: 
• Otimização para as necessidades de dados de uma aplicação específica.
• Pode incluir dados altamente especializados e formatados para uso direto pela aplicação.
• Facilita a integração e a análise de dados dentro do contexto da aplicação.
Conclusão
Os DataMarts são ferramentas poderosas para a análise de dados em áreas específicas de uma organização. Eles podem ser classificados de várias maneiras, dependendo de sua origem, arquitetura e finalidade. A escolha do tipo de DataMart a ser implementado deve levar em consideração as necessidades específicas da organização, bem como os recursos disponíveis para sua implementação e manutenção.
BANCOS DE DADOS:: 04.3 DataLake.
Origem do Data Lake
O conceito de Data Lake surgiu como uma evolução das necessidades de armazenamento e processamento de grandes volumes de dados, especialmente com o advento do Big Data. A ideia foi popularizada por James Dixon, CTO da Pentaho, que usou o termo para descrever um repositório de dados que permite armazenar dados em seu formato bruto, sem a necessidade de pré-processamento ou estruturação.
Conceitos de Data Lake
Um Data Lake é um repositório centralizado que permite armazenar dados em sua forma nativa, sejam eles estruturados, semiestruturados ou não estruturados. Diferente de um Data Warehouse, que requer a transformação e estruturação dos dados antes do armazenamento, um Data Lake permite a ingestão de dados em seu estado original. Isso oferece maior flexibilidade para análises futuras, pois os dados podem ser processados e transformados conforme necessário.
Tipos e Classificações de Data Lake
Os Data Lakes podem ser classificados de várias maneiras, dependendo de diferentes critérios como arquitetura, tipo de dados armazenados, e tecnologias utilizadas. Abaixo estão os principais tipos e suas características:
1. Arquitetura de Data Lake
• On-Premises Data Lake: Implementado dentro da infraestrutura física da organização. Oferece maior controle sobre os dados, mas pode ser caro e complexo de gerenciar.
• Cloud Data Lake: Hospedado em plataformas de nuvem como AWS, Azure, ou Google Cloud. Oferece escalabilidade, flexibilidade e geralmente é mais fácil de gerenciar.
• Hybrid Data Lake: Combina elementos de Data Lakes on-premises e na nuvem. Permite que as organizações aproveitem o melhor dos dois mundos, mantendo dados sensíveis on-premises enquanto utilizam a nuvem para escalabilidade e flexibilidade.
2. Tipo de Dados Armazenados
• Estruturados: Dados organizados em tabelas, como em bancos de dados relacionais.
• Semiestruturados: Dados que não seguem um esquema rígido, como JSON, XML, e logs.
• Não Estruturados: Dados que não têm uma estrutura predefinida, como vídeos, imagens, e documentos de texto.
3. Tecnologias Utilizadas
• Hadoop-based Data Lake: Utiliza o ecossistema Hadoop para armazenamento e processamento de dados. Inclui componentes como HDFS (Hadoop Distributed File System), MapReduce, e YARN.
• Data Lake baseado em Object Storage: Utiliza sistemas de armazenamento de objetos como Amazon S3, Azure Blob Storage, ou Google Cloud Storage. Oferece escalabilidade e flexibilidade.
• Data Lake baseado em Data Warehouse: Combina funcionalidades de Data Lakes e Data Warehouses, utilizando tecnologias como Snowflake ou Google BigQuery.
4. Propósito e Uso
• Enterprise Data Lake: Projetado para servir como um repositório central para toda a organização. Suporta múltiplos casos de uso e departamentos.
• Departmental Data Lake: Focado em atender as necessidades de um departamento específico dentro da organização, como marketing ou finanças.
• Personal Data Lake: Utilizado por indivíduos ou pequenos grupos para armazenar e analisar dados pessoais ou de pequenos projetos.
Características dos Tipos de Data Lake
On-Premises Data Lake
• Controle: Maior controle sobre a segurança e conformidade dos dados.
• Custo: Pode ser caro devido à necessidade de hardware e manutenção.
• Latência: Menor latência para acesso a dados locais.
Cloud Data Lake
• Escalabilidade: Facilmente escalável para acomodar grandes volumes de dados.
• Custo: Modelo de pagamento conforme o uso, potencialmente mais econômico.
• Flexibilidade: Fácil de integrar com outras ferramentas e serviços na nuvem.
Hybrid Data Lake
• Flexibilidade: Combina os benefícios de on-premises e cloud.
• Complexidade: Pode ser mais complexo de gerenciar devido à integração de diferentes ambientes.
• Segurança: Permite manter dados sensíveis on-premises enquanto utiliza a nuvem para dados menos críticos.
Hadoop-based Data Lake
• Open Source: Baseado em tecnologias open source, o que pode reduzir custos.
• Ecosistema: Rico em ferramentas e componentes para processamento de dados.
• Complexidade: Requer expertise técnica para implementação e manutenção.
Data Lake baseado em Object Storage
• Escalabilidade: Altamente escalável e flexível.
• Custo: Geralmente mais econômico devido ao modelo de pagamento conforme o uso.
• Integração: Fácil de integrar com outras ferramentas e serviços na nuvem.

BANCOS DE DADOS:: 04.4 DataMesh.
Origem do DataMesh
O conceito de DataMesh foi introduzido por Zhamak Dehghani em 2019, enquanto trabalhava na ThoughtWorks. Ele surgiu como uma resposta aos desafios enfrentados pelas organizações ao tentar escalar suas infraestruturas de dados tradicionais, que muitas vezes se tornavam gargalos devido à centralização e à falta de agilidade.
Conceitos do DataMesh
O DataMesh é uma abordagem descentralizada para a gestão de dados, que se baseia em princípios de design orientados a domínio, inspirados na arquitetura de microsserviços. Ele propõe uma mudança de paradigma, onde os dados são tratados como produtos e a responsabilidade pela sua gestão é distribuída entre as equipes que possuem o conhecimento do domínio.
Os principais conceitos do DataMesh incluem:
1. Domínio Orientado a Dados: Os dados são organizados em torno de domínios de negócios, e cada domínio é responsável por seus próprios dados.
2. Dados como Produto: Cada domínio trata seus dados como produtos, com equipes dedicadas a garantir a qualidade, disponibilidade e usabilidade dos dados.
3. Plataforma de Dados Autoatendimento: Uma infraestrutura que permite às equipes de domínio gerenciar seus dados de forma autônoma, sem depender de uma equipe centralizada.
4. Governança Federada: Um modelo de governança que equilibra a autonomia dos domínios com a necessidade de padrões e políticas organizacionais.
Tipos e Classificações do DataMesh
O DataMesh pode ser classificado de várias maneiras, dependendo do foco e da implementação. Abaixo estão os principais tipos e suas características:
1. Domínios de Dados
Os domínios de dados são unidades organizacionais que possuem e gerenciam seus próprios dados. Eles são classificados com base nas áreas de negócios ou funções específicas dentro da organização. Exemplos incluem:
• Domínio de Vendas: Gerencia dados relacionados a transações de vendas, clientes e produtos.
• Domínio de Marketing: Foca em dados de campanhas, leads e segmentação de mercado.
• Domínio de Finanças: Lida com dados financeiros, contabilidade e relatórios.
• Domínio de Recursos Humanos: Gerencia dados de funcionários, recrutamento e desempenho.
2. Plataformas de Dados Autoatendimento
Estas plataformas fornecem as ferramentas e infraestruturas necessárias para que os domínios gerenciem seus dados de forma independente. Elas podem ser classificadas com base nas funcionalidades oferecidas:
• Ingestão de Dados: Ferramentas para coleta e integração de dados de várias fontes.
• Armazenamento de Dados: Soluções para armazenamento escalável e seguro de dados.
• Processamento de Dados: Ferramentas para transformação e análise de dados.
• Catálogo de Dados: Sistemas para catalogar e descobrir dados dentro da organização.
• Segurança e Governança: Ferramentas para garantir a conformidade com políticas de segurança e regulamentações.
3. Governança Federada
A governança federada no DataMesh é uma abordagem híbrida que combina a autonomia dos domínios com a necessidade de conformidade organizacional. Ela pode ser classificada em:
• Políticas de Dados: Definição de políticas organizacionais que todos os domínios devem seguir.
• Padrões de Dados: Estabelecimento de padrões para formatos de dados, nomenclatura e qualidade.
• Monitoramento e Auditoria: Ferramentas e processos para monitorar o uso de dados e garantir a conformidade.
• Treinamento e Suporte: Programas para educar as equipes de domínio sobre melhores práticas e ferramentas de dados.
Características dos Tipos de DataMesh
Domínios de Dados
• Autonomia: Cada domínio tem controle total sobre seus dados.
• Especialização: As equipes de domínio possuem conhecimento profundo sobre os dados que gerenciam.
• Responsabilidade: Cada domínio é responsável pela qualidade e disponibilidade de seus dados.
Plataformas de Dados Autoatendimento
• Escalabilidade: Capacidade de crescer conforme a demanda aumenta.
• Flexibilidade: Suporte a múltiplas fontes e tipos de dados.
• Usabilidade: Ferramentas intuitivas que permitem às equipes de domínio gerenciar dados sem necessidade de expertise técnica profunda.
Governança Federada
• Equilíbrio: Combina autonomia com conformidade organizacional.
• Consistência: Garante que todos os domínios sigam padrões e políticas comuns.
• Transparência: Facilita a visibilidade e o controle sobre o uso de dados em toda a organização.
Em resumo, o DataMesh é uma abordagem inovadora para a gestão de dados que promove a descentralização e a autonomia
