BANCOS DE DADOS:: 02.3 Modelagens de dados nosql.
 -
**Origem e Conceitos de Modelagens de Dados NoSQL**

A modelagem de dados NoSQL surgiu como uma resposta às limitações dos bancos de dados relacionais tradicionais (SQL) em lidar com grandes volumes de dados, alta velocidade de leitura e escrita, e a necessidade de escalabilidade horizontal. Com o advento da web 2.0, redes sociais, big data e a Internet das Coisas (IoT), a necessidade de sistemas de banco de dados que pudessem lidar com dados não estruturados e semi-estruturados cresceu exponencialmente. NoSQL, que significa "Not Only SQL", refere-se a uma classe de sistemas de gerenciamento de banco de dados que não seguem o modelo relacional tradicional.

**Conceitos Principais:**
1. **Escalabilidade Horizontal:** Capacidade de adicionar mais servidores para distribuir a carga de trabalho.
2. **Flexibilidade de Esquema:** Permite a inserção de dados sem a necessidade de definir um esquema fixo.
3. **Alta Disponibilidade:** Sistemas projetados para minimizar o tempo de inatividade.
4. **Desempenho:** Otimizado para operações de leitura e escrita rápidas.
5. **Consistência Eventual:** Em vez de garantir a consistência imediata dos dados, alguns sistemas NoSQL garantem que, eventualmente, todos os dados serão consistentes.

**Tipos e Classificações de Modelagens de Dados NoSQL**

Os bancos de dados NoSQL podem ser classificados em quatro tipos principais, cada um com suas características e casos de uso específicos:

1. **Bancos de Dados de Chave-Valor (Key-Value Stores):**
   - **Características:** Armazenam dados como pares de chave-valor. A chave é única e usada para recuperar o valor associado.
   - **Exemplos:** Redis, DynamoDB, Riak.
   - **Casos de Uso:** Sessões de usuário, carrinhos de compras, cache.

2. **Bancos de Dados de Colunas (Column-Family Stores):**
   - **Características:** Armazenam dados em tabelas, linhas e colunas, mas diferem dos bancos de dados relacionais ao permitir que cada linha tenha um número diferente de colunas.
   - **Exemplos:** Apache Cassandra, HBase.
   - **Casos de Uso:** Análise de grandes volumes de dados, logs de eventos, sistemas de recomendação.

3. **Bancos de Dados de Documentos (Document Stores):**
   - **Características:** Armazenam dados em documentos, geralmente no formato JSON, BSON ou XML. Cada documento é uma unidade autônoma que pode conter dados complexos e aninhados.
   - **Exemplos:** MongoDB, CouchDB.
   - **Casos de Uso:** Gerenciamento de conteúdo, e-commerce, aplicativos móveis.

4. **Bancos de Dados de Grafos (Graph Databases):**
   - **Características:** Armazenam dados em nós, arestas e propriedades, permitindo a representação de relações complexas entre dados.
   - **Exemplos:** Neo4j, Amazon Neptune.
   - **Casos de Uso:** Redes sociais, sistemas de recomendação, detecção de fraudes.

**Detalhamento dos Tipos e Suas Características:**

1. **Bancos de Dados de Chave-Valor:**
   - **Redis:** Armazenamento em memória, extremamente rápido, suporta estruturas de dados como listas, conjuntos e hashes.
   - **DynamoDB:** Serviço gerenciado pela AWS, oferece escalabilidade automática e replicação de dados.
   - **Riak:** Distribuído, altamente disponível, baseado no modelo de consistência eventual.

2. **Bancos de Dados de Colunas:**
   - **Apache Cassandra:** Distribuído, escalável, projetado para alta disponibilidade sem ponto único de falha.
   - **HBase:** Baseado no HDFS (Hadoop Distributed File System), projetado para grandes tabelas dispersas.

3. **Bancos de Dados de Documentos:**
   - **MongoDB:** Flexível, permite consultas ad hoc, indexação e agregação de dados.
   - **CouchDB:** Utiliza JSON para armazenar dados, JavaScript para consultas e MapReduce para indexação.

4. **Bancos de Dados de Grafos:**
   - **Neo4j:** Utiliza o modelo de grafo de propriedade, permite consultas complexas e rápidas sobre relações.
   - **Amazon Neptune:** Serviço gerenciado, suporta os modelos de grafo Property Graph e RDF (Resource Description Framework).

Cada tipo de banco de dados NoSQL é projetado para atender a diferentes necessidades e casos de uso, oferecendo flexibilidade e desempenho onde os bancos de dados relacionais podem não ser a melhor escolha.
